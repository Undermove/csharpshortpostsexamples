# Стримить или не стримить: SSE, NDJSON и IAsyncEnumerable в ASP.NET Core — и когда это вообще нужно

Недавно мне попалась хорошая статья про [IAsyncEnumerable и стриминг данных](https://adrianbailador.github.io/blog/53-iasyncenumerable-csharp-streaming-data/). Завязка там бодрая: «прод упал, 500 000 записей, `List`, 8 ГБ RAM — математика не сошлась». Мораль: не загружай всё в память, стримь — и будет тебе счастье.

Статья правильная. Но у меня после неё осталось два чувства.

Первое: в таких статьях обычно рассказывают, как это **отдать** с бэкенда, и почти никогда — как это **принять** на фронте. А меня как раз цепляет вторая половина: насколько это удобно, что для этого вообще есть в браузере, какие варианты.

Второе: стриминг там подан как **оптимизация памяти**, которую надо натянуть на каждый `ToListAsync`. И вот с этим хочется не поспорить, а **дополнить**. Потому что, разобрав все сценарии до конца (включая неприятный — когда отдаёшь один здоровенный объект), приходишь к выводу: стриминг даёт выигрыш только в определённых сценариях. И выбирать его стоит скорее от бизнес-кейса, чем от абстрактного желания «что-нибудь соптимизировать».

Давайте разберёмся по-человечески, с обеих сторон и с замерами. Весь код — в [репозитории с примерами](https://github.com/) (ссылка в конце), там же k6-бенчмарки, которые можно прогнать самому.

> Контекст для примеров: у нас база знаний, статьи лежат в MySQL как JSON в `LONGTEXT`-колонке, одна статья ~234 КБ. Бэкенд — ASP.NET Core minimal API на .NET 10, EF Core + Pomelo, фронт — React.

---

## Как стриминг вообще работает: от базы до экрана

Сдвиг в голове простой: вместо «собери всё в память и отдай одним куском» — «отдавай поток».

По шагам, что физически происходит, когда мы стримим список:

1. **MySQL** шлёт строки результата по TCP **по одной**, отдельными пакетами, по мере того как находит. На проводе это байты, нарезанные на «пакеты-строки».
2. **MySqlConnector** читает эти пакеты из сокета по мере того, как ты просишь следующую строку, и собирает из байтов готовый объект. То есть стриминг с базы есть всегда — `ToListAsync` просто вычитывает **все** строки разом и складывает в `List`.
3. **EF Core** через `AsAsyncEnumerable()` отдаёт тебе строки по одной (`await foreach`).
4. Ты **пишешь** каждую в ответ и при желании флашишь.
5. **Kestrel** отправляет это как HTTP-чанки (chunked transfer encoding) по TCP браузеру.
6. **Браузер** получает байты по мере прихода. `fetch` отдаёт их через `response.body` — это поток (`ReadableStream`).

Ключевая мысль: на каждом стыке это просто байты, текущие по TCP. Чтобы получатель мог нарезать их обратно на объекты, нужно **обрамление** (framing) — договорённость, где кончается один объект и начинается следующий. Дальше вся разница между способами — именно в обрамлении и в том, кто его парсит.

## Способ 0: буфер (`ToListAsync`)

База для сравнения. Материализуем весь список и сериализуем одним JSON-массивом:

```csharp
app.MapGet("/articles", async (KbContext db, CancellationToken ct) =>
    Results.Ok(await db.Articles.AsNoTracking().ToListAsync(ct)));
```

Просто, понятно, работает — пока список небольшой. На больших выборках держим весь датасет в памяти, и клиент не видит ничего, пока не соберётся весь ответ.

## Способ 1: вернуть `IAsyncEnumerable<T>` напрямую

Самый ленивый стриминг. ASP.NET Core умеет сериализовать `IAsyncEnumerable<T>` как **стриминговый JSON-массив** — `System.Text.Json` пишет элементы по мере перечисления:

```csharp
app.MapGet("/articles", (IDbContextFactory<KbContext> factory, CancellationToken ct)
    => StreamArticles(factory, ct));

static async IAsyncEnumerable<Article> StreamArticles(
    IDbContextFactory<KbContext> factory,
    [EnumeratorCancellation] CancellationToken ct)
{
    await using var db = await factory.CreateDbContextAsync(ct);
    await foreach (var a in db.Articles.AsNoTracking()
                                       .AsAsyncEnumerable()
                                       .WithCancellation(ct))
        yield return a;
}
```

Ноль кода на «обрамление» — фреймворк всё делает сам. Но есть нюанс: на выходе это **обычный JSON-массив** `[{...},{...}]`. А `JSON.parse` на клиенте требует **целый** валидный массив — увидеть закрывающую скобку. То есть построчно, по мере прихода, его не распарсить: клиент всё равно ждёт конец. Для «отдать поменьше памяти на сервере» — годится. Для «фронт рисует по мере прихода» — нет.

Чтобы фронт мог потреблять данные инкрементально, нужен формат, где граница объекта явная. Их два популярных: NDJSON и SSE.

## Способ 2: NDJSON — простой до неприличия

**NDJSON (Newline-Delimited JSON)** — один JSON-объект на строку, разделитель — перевод строки. Весь «стандарт» помещается в эту фразу. Так отдают логи, дампы, bulk-эндпоинты Elasticsearch и часть стримов LLM.

### Бэкенд

Встроенного хелпера нет — пишем руками. Это буквально цикл: сериализовал → дописал `\n` → флашнул:

```csharp
app.MapGet("/articles", async (HttpContext http,
    IDbContextFactory<KbContext> factory, CancellationToken ct) =>
{
    http.Response.ContentType = "application/x-ndjson";
    await using var db = await factory.CreateDbContextAsync(ct);

    await foreach (var a in db.Articles.AsNoTracking()
                                       .AsAsyncEnumerable()
                                       .WithCancellation(ct))
    {
        await JsonSerializer.SerializeAsync(http.Response.Body, a, cancellationToken: ct);
        await http.Response.Body.WriteAsync("\n"u8.ToArray(), ct);
        await http.Response.Body.FlushAsync(ct); // выталкиваем строку клиенту сразу
    }
});
```

Ручной `FlushAsync` мне даже нравится: ты сам решаешь, когда строка уезжает в сокет, и тут же про неё забываешь — ничего не копится.

### Фронтенд

Встроенного парсера, как у SSE, нет. Берём `fetch`, у ответа есть `body` — это `ReadableStream`. Читаем кусками, копим в буфер, режем по `\n`, целую строку отдаём в `JSON.parse`. Загвоздка: границы сетевых чанков **не совпадают** с границами строк, поэтому недорезанный хвост держим до следующего чанка:

```ts
const res = await fetch("/articles");
const reader = res.body!.getReader();
const decoder = new TextDecoder();
let buffer = "";

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });

  let nl: number;
  while ((nl = buffer.indexOf("\n")) >= 0) {
    const line = buffer.slice(0, nl);
    buffer = buffer.slice(nl + 1);
    if (line.trim()) render(JSON.parse(line)); // готовый объект — рисуем сразу
  }
}
```

Выглядит как возня, но это десяток строк, которые пишешь один раз. А если лень — есть мелкие библиотеки вроде `ndjson-readablestream`, которые прячут цикл за `for await (const obj of ...)`.

**Плюсы:** работает где угодно — обычный POST, любые заголовки, любой HTTP-клиент (мобилка, бэк-ту-бэк, скрипт). Формат человекочитаемый, дебажится `curl`-ом.
**Минусы:** нет встроенного парсера и авто-реконнекта; нет именованных событий из коробки (хочешь типы — тегируй строки полем `type`); это договорённость, а не стандарт.

## Способ 3: SSE — самый «из коробки» для браузера

**Server-Sent Events** — это одно долгоживущее HTTP-соединение, по которому сервер «капает» события. Формат кадра стандартизирован (`data: ...\n\n`, плюс необязательные `event:`, `id:`, `retry:`), и — главное — в браузере **уже есть** парсер этого формата.

### Бэкенд

В .NET 10 это, по сути, одна строчка — `TypedResults.ServerSentEvents`. Хелпер сам сериализует объект в `data:` и оборачивает в SSE-формат:

```csharp
app.MapGet("/articles", (IDbContextFactory<KbContext> factory, CancellationToken ct)
    => TypedResults.ServerSentEvents(Stream(factory, ct)));

static async IAsyncEnumerable<SseItem<Article?>> Stream(
    IDbContextFactory<KbContext> factory,
    [EnumeratorCancellation] CancellationToken ct)   // ct = RequestAborted
{
    await using var db = await factory.CreateDbContextAsync(ct);
    await foreach (var a in db.Articles.AsNoTracking().AsAsyncEnumerable().WithCancellation(ct))
        yield return new SseItem<Article?>(a, "article");

    yield return new SseItem<Article?>(null, "done"); // по нему фронт закроет соединение
}
```

### Фронтенд

Никакой библиотеки — встроенный `EventSource`. Открыл, повесил обработчик, внутри `JSON.parse(e.data)`:

```ts
const es = new EventSource("/articles");

es.addEventListener("article", (e) => render(JSON.parse(e.data)));

// Стрим закончился — закрываемся сами, иначе EventSource переподключится.
es.addEventListener("done", () => es.close());
```

Это, на минуточку, ровно та механика, на которой стримит ответы ChatGPT.

**Плюсы:** встроенный парсер в браузере, именованные события (`meta` / `article` / `done`), авто-реконнект.
**Минусы и грабли:**
- `EventSource` умеет только `GET` без кастомных заголовков. Нужен `POST` или токен в заголовке — берите [`@microsoft/fetch-event-source`](https://www.npmjs.com/package/@microsoft/fetch-event-source).
- `axios` сюда не умеет — у него нет потокового чтения событий.
- Авто-реконнект — палка о двух концах: когда стрим закончился, надо явно сказать клиенту «всё» (событие `done` + `es.close()`), иначе он переподключится и начнёт качать заново.
- Не забудьте `CancellationToken`. Соединение живёт долго; если клиент отвалился, а токен не проброшен, сервер продолжит тянуть строки из БД в никуда. В minimal API токен прилетает в хендлер автоматически (это `RequestAborted`).

## Замер: буфер против стримов

Хватит теории. Прогнал [k6](https://k6.io/): 8 виртуальных пользователей, 12 секунд непрерывной нагрузки, ответ ~47 МБ у всех трёх вариантов одинаковый. Пик памяти сервера снимал из встроенного семплера кучи.

| Вариант | Пик кучи | TTFB (`http_req_waiting`) | Throughput |
|---|---:|---:|---:|
| `list` (буфер) | 1483 МБ | 1.34 с | 255 МБ/с |
| `ndjson` | 557 МБ | 62 мс | 267 МБ/с |
| `sse` | 208 МБ | 89 мс | 210 МБ/с |

Что тут важно:

- **Память** у стримов в разы меньше. А под жёстким лимитом кучи (`DOTNET_GCHeapHardLimit`) буфер на 500 статей просто падает с `OutOfMemoryException`, пока стримы спокойно отдают свои 117 МБ.
- **Первый байт** у буфера ≈ полному времени ответа: он сидит и материализует весь список, прежде чем выдавить хоть байт. У стримов — десятки миллисекунд.
- **Пропускная способность** у всех примерно одинаковая.

Вывод, который стоит запомнить: стриминг выигрывает **память** и **задержку первого байта**, но **не пропускную способность**. Если кто-то продаёт вам стриминг как «быстрее» — он лукавит.

## Подводные камни стриминга (где он тихо ломается)

Прежде чем бежать переписывать всё на стрим, пара вещей, без которых «стрим» превращается обратно в буфер:

- **`AsNoTracking()` обязателен.** Иначе change tracker удержит каждую сущность, и набор всё равно осядет в памяти целиком.
- **Контекст из `IDbContextFactory`, а не scoped.** `IAsyncEnumerable` перечисляется уже после выхода из обработчика, и scoped-контекст успел бы закрыться прямо посреди стрима.
- **`EnableRetryOnFailure` молча буферит** весь резалтсет — стратегия повторов не умеет переиграть наполовину прочитанный поток. На стриминговых запросах её быть не должно.

И самое неочевидное — **медленный консюмер**. Пока он по чуть-чуть вычитывает ответ, сервер вынужден держать открытым соединение с базой всё это время (он же тянет строки по мере отдачи). Поставил пул в 3 соединения, натравил 5 медленных клиентов:

| Вариант | 5 медленных клиентов, пул = 3 |
|---|---|
| `ndjson` (стрим) | 3 × `200`, 2 × `500` — пул исчерпан |
| `list` (буфер) | 5 × `200` — все успешны |

Стрим держит соединение с БД весь медленный ответ и выжирает пул. А буфер прочитал всё залпом за миллисекунды, **отпустил соединение** и дальше неспешно слал из памяти. Парадокс: буфер, которого мы только что хоронили, под медленного клиента ведёт себя приличнее.

Мораль: вопрос не «стрим или буфер вообще», а **чего у вас дефицит — памяти или соединений к базе**.

## А может, просто пагинация?

Закономерный вопрос: если со стримингом столько нюансов, может, ну его, и всегда пагинировать?

Для обычного списка, который листает интерфейс — да, **пагинация почти всегда правильный дефолт**. Клиент тянет по N, соединение отпускается мгновенно, страницы кэшируются и ретраятся, на сервере ничего не висит. Берите keyset (курсор по последнему id, без `OFFSET` — он на больших смещениях заставляет базу перелопачивать и выбрасывать прочитанное):

```csharp
app.MapGet("/articles/page", async (KbContext db, int? after, int take, CancellationToken ct) =>
{
    var items = await db.Articles.AsNoTracking()
        .Where(a => a.Id > (after ?? 0))
        .OrderBy(a => a.Id)
        .Take(take)
        .ToListAsync(ct);

    return Results.Ok(new
    {
        items,
        nextCursor = items.Count > 0 ? items[^1].Id : (int?)null,
        hasMore = items.Count == take
    });
});
```

Но пагинация держится на одном допущении: есть **конечный снимок данных**, который можно нарезать страницами. И есть два класса задач, где это допущение разваливается — там стрим незаменим:

1. **Выгрузить или обработать ВСЁ за один проход** — экспорт, отчёт, ETL, «отдай все 500 000 строк файлом». Пагинировать такое — это N запросов, клиент-оркестратор и пляски с курсором; стрим делает это одним запросом на постоянной памяти.
2. **Данные в реальном времени** — живая лента, логи, прогресс задачи, токены от LLM. Тут нет «страницы N»: данные ещё рождаются, клиент физически не может запросить страницу будущего.

## Отдельная боль: один здоровенный объект

Всё выше — про **количество** (много объектов). Но бывает беда другого рода: объект **один**, но жирный. У нас это статья на 234 КБ JSON-ом в одной ячейке. `IAsyncEnumerable` тут бесполезен — объект-то один, дело не в числе строк, а в размере одной.

### Где это лежит в MySQL

Большой `LONGTEXT`/`JSON` в InnoDB (дефолтный формат строки `DYNAMIC`) в строку не влезает и [уезжает off-page](https://dev.mysql.com/doc/refman/8.0/en/innodb-row-format.html): в самой записи остаётся 20-байтный указатель, а значение целиком — в overflow-страницах. Сам MySQL с этим справляется.

### Что творится в .NET при чтении

Наивно (EF, `GetString`) — весь объект материализуется в одну `string`. А строка в .NET это UTF-16, 2 байта на символ, так что 234 КБ — это здоровенный объект далеко за порогом 85 000 байт. И всё, что `≥ 85 000` байт, попадает в [Large Object Heap](https://learn.microsoft.com/dotnet/standard/garbage-collection/large-object-heap). А LOH собирается только при полной gen2-сборке и по умолчанию **не компактится** — то есть жирные строки живут дольше всех и фрагментируют кучу.

### Очевидный фикс — и засада

Логично сказать: возьму `SequentialAccess` + `GetTextReader`, и пусть течёт. Не выйдет. У MySqlConnector `GetTextReader` внутри буквально вот что:

```csharp
public override TextReader GetTextReader(int ordinal)
    => new StringReader(GetString(ordinal));   // весь LONGTEXT уже материализован в LOH
```

То есть он сначала материализует весь объект в `string` (привет, LOH), и только потом оборачивает в `StringReader`. Ридер дали — а толку ноль. Я сам на это чуть не купился.

### Что реально стримит

На MySqlConnector честно течёт только `GetStream`, а он работает с **бинарными** колонками. Значит, если объект надо отдавать потоком — храните его как `BLOB`/`LONGBLOB`, а не `LONGTEXT`. Тогда `SequentialAccess` + `GetStream` читает мелкими буферами мимо LOH, и вы льёте байты прямо в `Response.Body`:

```csharp
app.MapGet("/article/{id:int}/raw", (int id, KbContext db, CancellationToken ct) =>
    Results.Stream(async body =>
    {
        var conn = db.Database.GetDbConnection();
        await conn.OpenAsync(ct);
        await using var cmd = conn.CreateCommand();
        cmd.CommandText = "SELECT ContentBlob FROM articles WHERE Id = @id";
        cmd.Parameters.Add(new MySqlParameter("@id", id));

        await using var reader = await cmd.ExecuteReaderAsync(
            CommandBehavior.SequentialAccess | CommandBehavior.SingleRow, ct);

        if (await reader.ReadAsync(ct))
            await using (var src = reader.GetStream(0))   // настоящий поток, объект целиком в память не лезет
                await src.CopyToAsync(body, ct);
    }, "application/json"));
```

### Замер большого объекта

k6, 8 потоков, по 5000 запросов на одну статью:

| Способ | Аллокаций | Полных (gen2) сборок | TTFB p95 |
|---|---:|---:|---:|
| `GetString` (EF) | 6079 МБ | 125 | 27 мс |
| `GetTextReader` | 3891 МБ | 89 | 16 мс |
| `GetStream` (BLOB) | 1550 МБ | 32 | 13 мс |

`GetTextReader` аллоцирует на ~0.5 МБ на запрос больше, чем `GetStream` — это ровно та самая 234 КБ-строка (≈0.47 МБ в UTF-16), которую он зря тащит в LOH. Эмпирически подтверждено: `GetTextReader` **не стримит**.

### Что значит «фрагментирует кучу» на практике

Каждая лишняя большая строка летит в LOH, а собрать её можно только полной gen2-сборкой — у `GetString` их вчетверо больше, чем у `GetStream`. Современный .NET с [фоновой сборкой](https://learn.microsoft.com/dotnet/standard/garbage-collection/background-gc) намертво не фризит — gen2 идёт на отдельном потоке. Но это не бесплатно: больше CPU на GC, скачки латентности (p95 27 против 13 мс), распухший рабочий набор, фрагментация LOH. Если такие тяжёлые чтения идут регулярно поверх обычной нагрузки — прод не падает, а тихо потряхивает на p99 и жрёт память. Та самая деградация, которую потом полдня ищешь.

> И да, по уму большие объекты вообще хранят в объектном сторадже (S3 и компания), а в БД держат только ссылку. Но если исторически оно уже в базе и выносить пока не планируется — стримьте колонку как `BLOB`, не материализуйте.

## Вывод: стриминг — это про бизнес-кейс, а не про «соптимизировать»

Возвращаясь к исходной статье. Она права: стриминг действительно снижает нагрузку на память. Но это лишь часть картины, и если воспринимать его как «фичу для экономии памяти, которую надо включить везде» — легко получить обратный эффект.

Собрав все сценарии вместе:

- **Стриминг реально экономит память** — отдаём по строке, весь набор в куче не держим. Но это не магия: каждую строку мы всё равно материализуем в объект, footprint ≈ одна строка, а не zero-copy.
- **Аккуратнее с медленными читателями** — они форсят удержание соединения с базой, и пул недолго выжрать. Иногда буфер безопаснее.
- **Пагинация** — зачастую лучший компромисс для интерактивных списков: и память не грузит, и реализуется тривиально.
- **Стриминг стоит выбирать от бизнес-кейса**, а не от желания оптимизировать: онлайн-логи, ответы LLM на лету, прогресс задач, выгрузка всего одним проходом. Память он экономит — но это приятный бонус, а не повод.

Иначе говоря: стриминг — это один из способов реализовать бизнес-логику, который **заодно** экономит память. Но только если ваш сценарий под него заточен. А «отдать список на 20 объектов в админке» — это по-прежнему честный `ToListAsync`, и не надо выдумывать себе проблем.
