# Стриминг списка: list vs ndjson vs sse

Пример к каналу **C# Short Posts**. Один и тот же список статей из MySQL, отданный
тремя способами, с замерами памяти и разбором, что происходит при медленном консюмере.

Данные: статьи лежат в MySQL как JSON в `LONGTEXT`-колонке, одна статья ~234 КБ.
Сидятся при старте (по умолчанию 500 штук ≈ 117 МБ).

## Три варианта

| Эндпоинт | Как отдаёт | Память на сервере |
|----------|------------|-------------------|
| `GET /articles/list` | буфер: `ToListAsync` → весь JSON-массив разом | пик = весь датасет |
| `GET /articles/ndjson` | стрим: по объекту на строку (NDJSON), флашим сразу | ≈ одна строка |
| `GET /articles/sse` | стрим через `TypedResults.ServerSentEvents` (.NET 10) | ≈ одна строка |

Все три берут одни и те же данные через один и тот же запрос (`Query`) и поддерживают
`?count=` (сколько статей отдать).

- **list** — `ToListAsync` материализует ВСЕ статьи в память и только потом сериализует. Клиент не видит ничего до конца.
- **ndjson** — `await foreach` по `AsAsyncEnumerable()`, каждую статью пишем в ответ и флашим. Клиент парсит построчно по мере прихода.
- **sse** — тот же `IAsyncEnumerable`, но завёрнут встроенным хелпером .NET 10: он сам сериализует объект в `data:` и сам делает SSE-обёртку. Браузер читает нативным `EventSource`.

## Запуск

```bash
docker compose up -d mysql                       # MySQL 8
ASPNETCORE_URLS=http://localhost:5005 dotnet run -c Release
cd client && npm install && npm run dev          # http://localhost:5173
```

## Бенчмарк памяти (k6)

Нагрузку гонит k6 (`bench.k6.js`), латентность/throughput — из его отчёта; пик памяти
сервера берём из семплера через `/memory` (читаем в `teardown`, сброс компактит LOH).

```bash
for v in list ndjson sse; do ENDPOINT=/articles/$v k6 run bench.k6.js; done
```

**8 VU, 12 c непрерывной нагрузки, count=200** (ответ ~47 МБ, одинаковый для всех трёх):

| variant | пик кучи | TTFB (`http_req_waiting`) | `http_req_duration` | throughput |
|---------|---------:|--------------------------:|--------------------:|-----------:|
| list   | 1483 МБ | avg 1.34 с | avg 1.39 с | 255 МБ/с |
| ndjson |  557 МБ | avg 62 мс  | avg 1.33 с | 267 МБ/с |
| sse    |  208 МБ | avg 89 мс  | avg 1.69 с | 210 МБ/с |

Стрим ест в разы меньше памяти и отдаёт первый байт в ~20 раз быстрее. У буфера TTFB почти
равен полному времени ответа — он шлёт всё только в самом конце. Throughput у всех сопоставимый:
стрим выигрывает по памяти и латентности первого байта, а не по пропускной способности.

**Под жёстким лимитом кучи** (`DOTNET_GCHeapHardLimit=0x10000000`, 256 МБ), один запрос на 500 статей:

```
ndjson → HTTP 200       sse → HTTP 200       list → HTTP 500 (System.OutOfMemoryException)
```

Буфер не влезает в лимит и падает; оба стрима спокойно отдают все 117 МБ.

## Медленный консюмер — и когда буфер ВЫГОДНЕЕ

Тут самое интересное. Стрим под медленного клиента включает backpressure (TCP-флоу-контроль
тормозит сервер), память остаётся низкой. Но есть обратная сторона.

(k6 для этого не годится — он не умеет троттлить чтение тела, поэтому медленного консюмера
эмулируем через `curl --limit-rate`.)

**Память: 6 параллельных медленных клиентов** (читают ~3 МБ/с):

| variant | пик кучи |
|---------|---------:|
| ndjson | ~114 МБ (ровно, как при одном клиенте) |
| sse    | ~320 МБ |
| list   | ~440 МБ (масштабируется с числом клиентов) |

Буфер держит ВЕСЬ датасет в памяти всё время медленной отдачи, и это умножается на число
клиентов → дорога в OOM. Стрим (ndjson) остаётся плоским независимо от числа клиентов.

**Соединения с БД: пул из 3, 5 параллельных медленных клиентов:**

```
ndjson (стрим)  → 3×200, 2×500   ← пул исчерпан: стрим держит соединение весь медленный ответ
list   (буфер)  → 5×200          ← прочитал всё за мс, отпустил соединение, дальше шлёт из RAM
```

**Вывод (ответ на «может, выгоднее отдать всю пачку?»):**
- Большие ответы, упёрся в память → **стримь** (list умрёт по памяти).
- Медленные/многочисленные консюмеры, упёрся в пул соединений → **буфер** (или стрим в очередь/пагинацию) безопаснее: стрим залипает на соединении весь медленный ответ.

То есть выбор — это не «стрим всегда лучше», а «что у тебя дефицит: память или соединения к БД».

## Эндпоинты

| Метод | Что |
|-------|-----|
| `GET /articles/list?count=` | буфер, JSON-массив |
| `GET /articles/ndjson?count=` | стрим NDJSON |
| `GET /articles/sse?count=` | стрим SSE |
| `GET /memory`, `POST /memory/reset` | семплер кучи (reset компактит LOH) |

## Подводные камни (учтены в коде)

- **`AsNoTracking()` обязателен** — иначе change tracker удержит каждую статью, и «стрим» снова забьёт память всем датасетом.
- **Контекст из `IDbContextFactory`, а не scoped** — `IAsyncEnumerable` перечисляется уже после выхода из обработчика; scoped-контекст закрылся бы посреди стрима.
- **`EnableRetryOnFailure` молча буферит** весь резалтсет (retry не умеет повторить наполовину прочитанный стрим) — на стриминговых запросах его быть не должно.
- **SSE авто-реконнектится** — поэтому в конце шлём событие `done`, и фронт по нему закрывает `EventSource`.

## Фронт (React + Vite)

Три кнопки — List / NDJSON / SSE — на одних данных: list держит экран пустым до конца и
вываливает всё разом, ndjson и sse рисуют статьи по мере прихода. SSE — через нативный
`EventSource` (никакого ручного reader/буфера), закрывается по событию `done`.
